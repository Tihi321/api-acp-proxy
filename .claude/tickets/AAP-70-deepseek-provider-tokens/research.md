# AAP-70 research: deepseek provider + token logic for deepseek and ollama

## Question

How do usage numbers, output limit, prompt-size limit and usage-limit/balance work today (ACP vs `LocalOpenAiProvider` vs Ollama), what does registering a provider take (template: commit d99bfb3, Ollama), and is `LocalOpenAiProvider` a good base for a cloud `deepseek` provider?

Marks: **C** = confirmed by reading code/running a command, **I** = inferred. DeepSeek API facts (endpoints, error codes, context sizes) are from model knowledge, not checked online: **I**, verify before planning.

## Answer (short)

- For Ollama (and every LocalOpenAiProvider) feature 1 (usage) and 2 (output limit) already work upstream-side; feature 3 (prompt cap) and 4 (usage limit/balance) do not exist. Gaps are mostly: no `checkPrompt`, no 429/402 -> `UsageLimitError` mapping, no `maxPromptChars`, usage store keeps only input/output (no cached/reasoning), chart has no colour for `ollama`.
- A thin, separate cloud class (or a `LocalOpenAiProvider` option set) is needed; do not reuse the class unchanged. Recommendation: extract/extend, see Base-class section.
- Registration of `deepseek` = copy the 15-file Ollama touch list below (plus chart colour, which Ollama skipped).

## Base-class recommendation

`LocalOpenAiProvider` is a workable base for the chat path (SSE parsing, usage/cached/reasoning extraction, max_tokens forwarding, Bearer header, `/models` listing, concurrency via router) but wrong in several local-only places (C unless marked):
- `baseUrl` ctor takes any URL and `apiKey` is optional; fine for https. Default `fetch` is `globalThis.fetch` (:92), fine for remote.
- "Not running" semantics: any connect failure -> `stopped` + 503 `local_server_not_running` with "start it from the app" text (:51-53, :189-193). For a cloud API this should be "unreachable"/`upstream_error` (502/503 `provider_unreachable`), never "start it". There is no `needs_login` state mapping for a missing/invalid key (ACP providers use `ProviderAuthRequiredError` -> `provider_auth_required`, provider.ts:~30; settings.ts:107-110 handles that code).
- 401/403 on chat is not mapped (503 upstream_error); 429/402 not mapped; 400 context errors not mapped.
- Class carries Gufo/Llama-only baggage (profiles, coordinator, embedding, images). Not harmful but noisy.
- `/models` of DeepSeek is available and cheap (I), so listing works; models have no context-window data, so `maxPromptChars` must come from a static table or setting.

Recommendation (I, for the planner): do NOT bolt cloud rules into `LocalOpenAiProvider` behind `if (id === "deepseek")`. Preferred: a small `CloudOpenAiProvider` in `src/providers/deepseek.ts` that extends `LocalOpenAiProvider` (make the needed private members `protected`: `headers`, `notRunning`, state/`setState`, `fetchImpl`, plus factor the SSE loop and `upstreamFailure` into overridable/shared helpers), overriding: not-reachable message/code, an error-mapping hook for HTTP status (401/403 -> `provider_auth_required`-style, 402 `Insufficient Balance` and 429 -> `UsageLimitError`, 400 context -> `promptTooLong`-like 400), `checkPrompt`/`maxPromptChars`, and a balance probe (`planLimits` for `GET /user/balance`, I). Put the shared token logic (checkPrompt, error-to-typed-error hook, `maxPromptChars` setting) in the base so Ollama gets it too (checkPrompt only; usage limit is n.a. for Ollama). Alternative (smaller diff, more branches): add an `upstreamErrorMapper` and `maxPromptChars` option to `LocalOpenAiOptions` and keep one class.

## Per-feature work implied (for the planner; options, not a plan)

1. Usage: already real for both; remaining: add `deepseek` chart colour; decide whether to store cached/reasoning in the usage store (needs `UsageCounts` schema change in usage-store.ts + `shared/ipc.ts` `UsageCountsView` + file version/`sanitize`, and the charts) — otherwise "recorded" = input/output only, same as ACP (C). DeepSeek reports `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens` and `completion_tokens_details.reasoning_tokens` for deepseek-reasoner (I): the current parser reads `prompt_tokens_details.cached_tokens` only (:250), so DeepSeek cache hits would be missed unless that field is added (I, verify live).
2. Output limit: forwarded already; DeepSeek caps `max_tokens` per model (deepseek-chat 8K, reasoner 64K as of my knowledge, I); a request over the cap gets an upstream 400 — decide clamp vs pass through. `runGeneration` chars/4 truncation also applies (see table).
3. Prompt limit: chars-based `maxPromptChars` is the existing key (per provider id in `providers.<id>.maxPromptChars`, effective value exposed on `provider.maxPromptChars`, router/ /v1/models/server pre-check are generic and already work for any provider that defines `checkPrompt`/`maxPromptChars`, C). Message text of `promptTooLong` says "The agent would silently drop the rest" (api.ts:589), wrong for deepseek/ollama (would need a variant message or parameter; keep prefix "The prompt is too long" for Scriptorium's regex, AAP-30 plan). It is per provider not per model; a context window is per model (deepseek-chat/reasoner 128K tokens ~ chars/4, I). Option: per-model table in the provider + setting override.
4. Usage limit/balance: needs (a) HTTP mapping 402/429 -> `UsageLimitError` in the provider's chat error branch (local-openai.ts:229-234 region); `track` then does the rest (exhaustion map, 429, card line, models, healthz) with the 60 min cooldown since DeepSeek gives no reset time (`exhaustedUntil(undefined,...)` -> cooldown, C usage-limit.ts:129-132); (b) the settings card for deepseek must render `usageLimitLine`; (c) optional: balance probe via `planLimits` (`PlanLimitsCache.supported` is `provider.planLimits`-based, I) and show on the card; DeepSeek "429" is plain rate limiting (not quota) and 402 is insufficient balance (I) so only 402 should mark exhausted, 429 rate limit should be a retryable error (decision needed). Exhaustion state is memory-only; it clears on first success (router.ts:244) or after cooldown.

## Risks / open questions

- DeepSeek API details (402 body, 429 semantics, `/user/balance` shape, model names, context/max output) are from memory; confirm against api-docs.deepseek.com before planning.
- Non-streaming clients get an aggregated stream; upstream `finish_reason` and usage handled; an error mid-stream arrives as `chunk.error` (:240) -> 503 `upstream_error`; a quota error before the stream is an HTTP status, handled in :229.
- Usage is wrong when `runGeneration` truncates at chars/4 (usage:null -> estimate) for a provider that forwards `max_tokens` upstream (also applies to current Gufo/Ollama).
- API key at rest: `mapSecrets` must list the new holder or the key is stored in plaintext (settings.ts:470, C). `SettingsView`/IPC returns the key to the renderer as the other providers do (I).
- Default `enabled` for deepseek: Ollama defaults true (local, harmless); a cloud provider without key should probably default false or show `needs_login`; there is no `needs_login` path for local-openai (C).
- `LocalServerId`-typed code (`targetKey`, coordinator, `local-servers`, monitor, `LOCAL_PROVIDER_IDS`) must not receive `deepseek`; no coordinator lease for a cloud provider (like Ollama).
- Per-model max concurrency / DeepSeek rate limits: unknown; the provider-level `maxConcurrent` cap is available.
- The settings window `settings-fields.test.ts` / `desktop-views.test.ts` contents not read: may need updating when views/fields are added.

## DeepSeek API facts (docs, 2026-11-28)

From the official DeepSeek API docs (api-docs.deepseek.com), read 2026-11-28 by the director's web-fetch piece. These replace the "from memory (I)" DeepSeek statements above.

- Base `https://api.deepseek.com` (no `/v1` documented). Endpoints: `POST /chat/completions`, `GET /models`, `GET /user/balance`. Auth: `Authorization: Bearer <key>`.
- Models: `deepseek-flash` (V4.1-Flash; vision, input text + image) and `deepseek-v4-pro` (text only). Legacy ids `deepseek-v4-flash` and `deepseek-v4-flash-vision-exp` are still accepted. Context 1,048,576 tokens for both; max output 393,216 tokens. `max_tokens` default: 8K non-thinking, 64K thinking, 128K at effort `max`.
- Thinking is a request parameter: `thinking: {type: "enabled" | "disabled"}`, `reasoning_effort: "none" | "low" | "high" | "max"` (`minimal` -> `low`, `medium` / `xhigh` -> `high`). Default: thinking on, effort `high`. Output: `message.reasoning_content`; stream: `delta.reasoning_content`. With `tools`, the earlier `reasoning_content` must be sent back in the assistant messages, otherwise 400.
- `usage`: `prompt_tokens`, `completion_tokens`, `total_tokens`, `prompt_tokens_details.cached_tokens`, `prompt_cache_hit_tokens`, `prompt_cache_miss_tokens`, `completion_tokens_details.reasoning_tokens`. Stream: the last chunk (the one with `finish_reason`) carries `usage` even without `include_usage`. `stream_options` without `stream: true` -> 400.
- `max_completion_tokens` is not documented: send `max_tokens` only. `response_format: {type: "json_object"}` supported; tools supported; `temperature` ignored in thinking mode.
- Errors: 400 invalid format, 401 authentication failed, 402 insufficient balance, 422 invalid parameters, 429 rate limit reached, 500 server error, 503 server overloaded. The error body shape is not documented (check live). `finish_reason`: `stop`, `length`, `content_filter`, `tool_calls`, `insufficient_system_resource`, `aborted`.
- Balance `GET /user/balance`: `{"is_available": bool, "balance_infos": [{"currency": "CNY" | "USD", "total_balance": "110.00", "granted_balance": "10.00", "topped_up_balance": "100.00"}]}` (amounts are strings).
- Pricing per 1M tokens (USD, off-peak / peak): flash cache hit 0.003 / 0.006, miss 0.15 / 0.3, output 0.6 / 1.2; v4-pro cache hit 0.022 / 0.044, miss 0.66 / 1.32, output 1.98 / 3.96. (Cost display is out of scope for AAP-70.)
